# KNOWN ISSUES

## 1. 引擎与原规范不一致（决策项，非 Bug）

用户提供的执行手册指定 UE5 + C++。实测本机：

| 检查项 | 结果 |
|---|---|
| Epic Games / UE 安装 | 不存在 |
| C 盘剩余 | 16 GB（UE5 引擎 + 城市工程需 100 GB+） |
| GPU | RTX 5060 Laptop 16 GB — 足够 |
| Godot | 4.4.1 stable 可用，headless 可验证 |

**决策**：改用 Godot 4.4.1 实现可运行的 Vertical Slice。
理由：手册第三十四条要求"优先保证最终项目可以真正运行""不要伪装成已经完成"。
在此环境写 UE5 C++ 产出的是一堆无法编译、无法运行、无法验证的代码，
正好违反手册自身的验收标准。

**UE5 技术 → 本项目替代方案**

| UE5 | Godot 实现 |
|---|---|
| Nanite | 合并网格 + 程序化立面着色器（一个 chunk 一次 draw call 画出全部窗格） |
| Lumen | 天空 IBL + 屏幕空间反射 + 移动反射探针（SDFGI 在高质量档） |
| Virtual Shadow Maps | 4 级联 PSSM 方向光阴影 |
| World Partition | 250 m chunk 流式加载 + 碰撞分层加载 |
| TSR / DLSS | MSAA + FSR 不可用 → `scaling_3d/scale`（部分实现） |
| Niagara | GPUParticles3D |
| Mass AI | MultiMesh 人群 + 轻量代理状态机 |
| PCG Framework | GDScript 程序化格网（对偶图街区） |
| GAS | 不做（待实现） |
| Chaos Vehicles | VehicleBody3D + VehicleWheel3D 光线投射车辆物理 |

## 2. 未消除的性能缺口（P7 判"部分实现"的唯一原因）

单 chunk 构建 17.3 ms，仍是 7 ms 帧预算的 2.5 倍。因为一次构建不可拆分，
流式器每帧最多建一个 chunk，所以加载期实测 15-29 FPS，约 6 s 后回到 45-55 FPS。

| 阶段 | 实测 | 还能做什么 |
|---|---|---|
| blocks 8.3 ms | 12 种街区的真实几何生成，无冗余查询（`CellFacts` 已缓存） | 只能靠线程构建：`ChunkBuilder` 目前是 GDScript 静态函数且读写 `CityData` 的共享缓存，非线程安全 |
| ground 7.7 ms | 其中 water 5.4 ms 集中在沿江 chunk（内陆 chunk 约 1.9 ms） | 江面距离场预计算（膨胀集已有，缺精确值的粗-精两级化） |
| streets 0.9 / furniture 0.4 ms | 已按 ring 用 `detail` 开关裁剪 | — |

**已试过并回退的方案**：把远处 chunk 的地面网格从 25 m 放宽到 50 m，ground 从 8.0 降到 3.5 ms，
但相邻 chunk 的边顶点不再重合，高架底部出现可见裂缝与竖向穿帮 —— 共享顶点优先于省采样，已回退。

## 3. 量化副作用（可接受，但必须记账）

- 距离/强度/公园/区划四类查询走 25 m 量化备忘格，岸边判定可偏移至多 25 m。
  因此 `in_water` 刻意走**精确**路径（角色、桥梁/隧道判定、出生点都依赖它），
  批量生成才用量化版 `water_dist_q`。
- 行政区归属按 100 m 取整缓存，导致格心靠近区界时街区类型可能翻转：
  普查数字相对量化前为 plates 7317→7316、edges 10531→10529，cells 不变。
- 地面泥滩带（宽 14 m）按节点而非格心判定，岸线呈 25 m 阶梯；
  该带几乎完全在水面之下，暂不处理。

### 4a. 画质复核后仍然不像的部分（2026-10-01 实拍对比后记账）

曝光、间接光、接触阴影、窗光能量、铺装分格、角色材质这一轮已经改到能看出差别；下面这些
仍然是"卡通"的成因，且都不是靠再调一次曝光能解决的：

- **树不再是绿色团块，但仍然不会动。** 悬铃木重做成"截头树"的真实形状：根颈外扩、通直树干、
  截头瘤、3 根上展主枝、5-6 个分色冠团（`CellProgram.tree`，玩家放置的 `Props.plane_tree` 现在
  调用同一个生成器，不再各画一份）。仍然缺：风（枝叶摆动）、半透明叶片与真正的枝叶层次——
  现在是分块的体块冠，近看仍是"雕出来的树"而不是"长出来的树"。
- **行人不再滑行，但也没有骨骼动画。** 四条腿臂各两节、肘与膝在轮廓里存在，步态按**每个 agent
  自己的相位**推进（相位随行走速度，所以通勤者腿频真的比散步者快），四相位实例分桶取代了
  原来"全场同时换姿势"的行进band效果。仍然缺：上身反向扭转、头部摆动、脚跟着地-脚尖离地的
  踝关节，以及跑与走的步幅差异。
- **玩家角色与行人同源问题已修，但没有面部与手指。** 躯干原来是一颗胶囊（胶囊没有肩、没有腰、
  没有胯，这正是"蛋"的来源），现在胸腔向肩外扩、骨盆独立、有颈、四肢两节且**关节在节点原点**
  ——腿从髋摆、臂从肩摆，脚随腿走。仍然缺：面部、手指、布料模拟、鞋与地面的接触阴影细节。
- **高架桥体已经有构件，但梁底仍然偏亮。** 断面从"一整块 1.3 m 平墙"改成闭合箱梁：翼缘板缝
  + 全宽梁底 + 收进 0.62 m 的腹板 + 更窄的主梁底，每 28 m 一道深色横隔梁与两支排水嘴，
  墩柱加了扩大基础、盖梁重新坐位、梁底与盖梁之间加暗色支座垫板（`MajorRoads._viaduct/_joints/_piers`）。
  代价按实测记账：全局道路构件网格 193 376 → 398 988 三角面（142.4 km 桥长，即 1.36 → 2.80 面/米），
  仍是一个 draw call。仍然缺的：**梁底在画面里仍接近受光面的亮度**。已定位原因不是曝光——
  把天空环境光降到 0.22 倍后整帧亮度小数点后四位完全不变（SDFGI 开着时 `ambient_light_*` 实际不参与），
  所以这是 SDFGI 探针分辨率不足以分辨 1.9 m 深的箱室，属于引擎侧限制，不是调参能解决的；
  本轮改用"梁底/主梁底两级更暗的反照率"部分补偿（同机位该区域亮度 0.729 → 0.588）。
- **天空没有云。** `ProceduralSkyMaterial` 只有梯度，晴天尚可，但"晴 0%"时头顶是一片均匀的蓝灰，
  缺少尺度参照物，远景因此显得平。加云需要程序化云层（或卷云贴图，仍属自制资产）。
- **广场铺装在中远景仍然偏亮偏平。** 板间色差与骨料已经加了，但大尺度上仍缺少落叶、污渍、
  轮胎痕与施工补丁这一类"城市痕迹"。
- **玻璃幕墙缺少反射内容来源。** SSR 只能反射已渲染的几何，天空以外的反射经常是空的，
  所以近处幕墙的镜面感仍然弱于实拍。
- **代价被记账了。** 角色与树的面数上升让全城三角面 702k → 770k（+9.7%），实测同场景 FPS
  58-69 未跌出既有区间；`MAX_CHUNK_BUILD_MS=25` 与流式 30 s 两项门禁仍通过（见 PROJECT_STATUS
  实测段）。若后续再加植被层次，应先降 LOD 而不是抬门槛。

## 5b. 城市模拟（Part 8）的真实边界

不是"待办"，是当前实现**确实不具备**的能力，避免被 `--sim-test` 的绿灯误读成已完成：

- **模拟是区级（11 个桶）而不是个体级**。一个"家庭"代表整区全部住户，因此不存在"某个 NPC
  涨工资后换了住处"这类个体后果；个体只通过 `crowd_factor` / `car_factor` 被聚合影响。
- **劳动力供给无弹性**。`labor = 0.62 × 区人口` 是播种常量，不随工资、失业或房价变化，
  所以模型里没有"劳动力参与率"这一层。
- **无跨区通勤结算**。工资与消费都发生在同一个桶内，产业与居住被混在一格里。
- **无信用与破产清算**。商铺账面可以为负（负债），但没有任何机制把它变成"关门并被替换"，
  只有连续亏损计数会一家家关掉它。
- **价格影响需求，不影响供给成本**。除工资与租金分成外，一切成本为常数。
- **状态不落盘**。`snapshot()/restore()` 只活在内存里；后端三代存档尚未接入，重启回到播种态。
- **结构变化慢于一次会话**。就业占比实测 8760 模拟小时为 0.16、87600 小时为 0.31，
  因为开店节奏被 `OPEN_AFTER=6` 限制为每类别每 6 小时一家。这是设计选择，但它意味着玩家
  在一次游戏内看到的是开关店事件，而不是产业结构迁移。

## 5c. 创作系统（Part 9）的真实边界

- **分区阈值是我定的，不是标定出来的。** 建成度 0.72 / 0.45 / 0.20 与四档体量上限（9 / 26 / 44 /
  80 m）来自"核心区不许塔楼、外围给整街区"这一意图，尚无玩家数据或美术评审依据；改它们必须
  同时改 `--validate-test` 的断言，否则门禁会替旧阈值站台。
- **商铺只在被模拟的 11 个街区内生效。** `CitySim.bootstrap` 只播种普查到的命名区，落在"郊区"
  的商业体不记账（现在会明确提示"未计入账本"，而不是静默吞掉）。
- **构件不参与缩放。** 长椅就是 1.8 m；缩放控制对 `kind=="prop"` 明确短路。要可变尺寸的构件，
  需要先把尺寸传进 `Props` 的每个生成器，而不是事后缩放节点。
- **预算只约束三角面，不约束件数与 actor。** 三角面阈值由生成器实测导出（约 3700 件混合作品
  封顶），`MAX_ACTORS` / `MAX_OBJECTS` 尚未定义。1000 件压力测试通过是因为它确实只花了约
  40 万三角面，不是因为件数被管住了。
- **地形上限已定义但无写入路径。** `CreationZones.MAX_TERRAIN` 目前只有读取方，地形工具本身
  未实现，所以这条上限现在是"承诺"而不是"事实"。

## 5d. 多人在线（Part 10）的真实边界

先说这一节存在的原因：Part 10 第一次交付时，Node 侧 19 条断言全绿，流水线 `PIPELINE: PASS`，
但**游戏客户端从未与服务器连接成功过**——客户端说 ENet + `var_to_bytes`，服务器说 TCP +
msgpack，两个协议栈各自自洽。测试用的是 Node 写的假客户端，复用服务器自己的框帧方式，所以
"多人可用"这个结论完全建立在没被测过的路径上。现在由 `Pipeline/mp_probe.sh`（真实 Godot
客户端，14 条断言）守住这条接缝。下面是在这条接缝之上仍然不成立的部分：

- **远端玩家现在会被渲染，但只是"一个站在复制坐标上的人"。** `RemoteAvatarLayer` 为兴趣范围内每个
  实体建一个程序化胶囊人，按 30 Hz 的复制流做指数平滑（>30 m 直接吸附，避免瞬移被画成飞行）。
  仍然没有的是：名字牌、垂直坐标（服务器只复制 x/z/yaw，所以远端玩家永远站在地面上，站在桥上
  的你会飘在半空）、脚步声、以及任何动画——走路时腿不动。Phase 234 的"互相看到"就此成立，
  Phase 177 的"移动必须平滑"只在水平面上成立。
- **两端移动模型不是同一个。** 服务器按 `6 m/s × dt` 积分，客户端角色有自己的加速度曲线。站着不动
  时误差恒为 0（已断言），但**冲刺或下坡时客户端可能比服务器跑得快而被回弹**。这条没有断言，
  属于已知未测风险；把它变成事实需要同步两端的移动模型，那是一次独立改动。
- **探针里的"第二名玩家"是同进程内的第二个客户端。** 它有自己的后端账号、自己的 socket、走完全
  相同的协议，因此复制与渲染链路是真的；但它没有独立的进程、独立机器与独立网络。跨进程双客户端
  尚未跑过。
- **传输是 TCP，不是 UDP/ENet。** 因此每条消息都可靠且有序，`SyncProtocol.CHANNEL_OF` 目前只是
  元数据加契约校验，不改变线上行为；弱网下移动包会触发队头阻塞。真实的不确定通道需要一个
  Godot  Dedicated Server 或 Node 侧原生 ENet 绑定，都会破坏当前的零依赖约束。
- **对账规则是"位移上界"而不是"回滚重放"。** 服务器只回答"我认为你现在在哪、这是第几个输入"，
  客户端比较的是自上次采样以来两端各自动了多少。真正的回滚重放需要两端跑同一个移动模型，
  那是上面那条未对齐风险的正解，目前没做。
- **单人钱包已经不是第二个事实来源，但联机入口仍依赖启动参数。** 此前 HUD 上的"现金 250000"
  是 `GameGlobals.cash`，全仓库没有任何地方写过它，而多人扣款走的是后端 append-only 账本
  （注册赠送 1000 分）——同一个玩家同时拥有两个互不相通的余额，且 HUD 那个永远不会减少。
  本轮删掉了 `cash`，钱包行改为只显示 `NetSession.balance_c`（只由服务器 `econ_event` 写入），
  未连接时明写"服务器未入账"。**仍未做**：没有登录/服务器地址输入界面，`NetSession.join()`
  依赖启动时的 `--backend=<url>` 提供 session token；单人模式下玩家没有钱包，创造不花钱，
  这个"单机免费"的规则也还没有在界面上说明。
- **价目表在服务器，模板清单在 GDScript。** R9 保证两边 id 一一对应，但价格本身仍是服务器单方面
  决定，客户端放置前看不到"这一下要花多少"。缺一个把价目下发给客户端并显示在 ghost 上的路径。
- **服务器侧的合法性校验是客户端规则的一份简化副本**（边界、水体、重叠）。真正的分区权限、
  三角面预算、遮挡检查只在 GDScript 里。副本会漂移——Phase 173 要的是唯一事实来源，这里目前是
  两个事实来源的折中。
- **当前是单实例。** 没有分区、没有跨服、没有匹配——两个客户端直连同一个 game_server。
  Phase 199-201 的 Region/Instance/Migration 均未实现。
- **NPC 和车辆不同步。** 服务器 tick 只复制玩家实体；NPC/车辆的多人同步需要把 CitySim
  从客户端搬到服务端，这是下一个切片的工作。
- **没有聊天、语音、好友、组队。** Phase 191-194 全部待实现。
- **反作弊是"速度上界 + 位移回弹 + 所有权"三件**，且回弹这条现在有证据（未经授权的 240 m
  位移被拉回服务器位置，偏差 < 1 m）。没有行为分析、没有统计检测、没有管理员 Dashboard，
  Phase 210-215 的大部分待实现。
- **世界状态持久化是单文件 JSON。** `world_creations.json` 足够证明闭环，但不是生产级存储。
  Phase 219 的多库分离未做。
- **建筑/经济操作是纯 request→confirm**，没有乐观更新。高速建造时有可感知的确认延迟——这是
  诚实的代价，不是遗漏。

## 5e. 主菜单（Phase 122 / 123）的真实边界

菜单现在是真的：无参数启动即挂载，四条入口背后都是已存在的系统（继续=隐藏面板、新游戏=
`CreationSystem.clear_all` 且清空结果落盘、画质=`QualityPresets.set_tier`、退出=`quit`），
Esc 能重新打开，11 条断言走 `choose()/set_quality()` 与鼠标同一条出口，窗口目视复核过真实点击。
仍然不成立的部分：

- **菜单不暂停世界，这是刻意选择，但玩家视角下它意味着"菜单开着时城市在自转"。** 暂停会让所有
  等 chunk 流式的门禁挂死，所以面板选择做覆盖层而不是暂停层；代价是菜单背后的人群与交通继续跑，
  站在菜单前看一分钟，城市已经过了一个小时。想要"暂停式菜单"需要先给门禁一个不依赖实时流式的
  等待条件，那是一次独立改动。
- **"继续"只是隐藏面板，没有存档/读档语义。** 它恢复的是本次进程里已经在跑的世界；进程关掉后
  能恢复的只有玩家层存档（`user://city_edits.json`），相机位置、时间、天气都不持久化。Phase 124
  的存档槽位未实现。
- **菜单项只有四条加画质。** 没有音量、分辨率、键位、语言——这些设置项本身还不存在，菜单不
  伪装它们。
- **"新游戏"没有二次确认。** 它会清空玩家层并立刻写盘；误点一次，本进程放置的所有作品就没了。
  加一个确认框是下一步最小的改进。
- **自带用户参数启动时不挂载菜单**（门禁与基准要和一个没有面板的城市比耗时和截图）。因此从
  命令行带参数启动的会话里，Esc 也打不开菜单——菜单实例根本不存在。

## 5f. 城市生命层（Part 12）的真实边界

这一层能跑、能算、能对上账，但**它不是"一百万个真人"**。以下九条是它现在的真实形状：

- **人口是队列，不是个人。** 442 万居民由 11 区 × (7 年龄段 + 5 职业阶段) ≈ 132 个整数表示，
  出生 / 死亡 / 老化 / 迁移都是速率在整日上的积分与余数结转。没有一个"具体的人"搬进上海；
  有名字、会饿、会花钱的个体只存在于 tier-0 的那几百个 agent 上。规范里"数据库模拟 100 万居民"
  达成的是**统计分辨率**，不是 100 万个对象。
- **一街一价。** 一个区一个类别只有一个 `price_c`，所以价格决定的是"这个人进不进这条街的门"，
  不能区分同一条街上的两家店。选址真正比较的是评分与步行距离。规范 P250 的"库存 / 员工数 /
  商品"未建模：员工数是每类常数（`STAFF_PER_SHOP`）。
- **NPC 的钱来自区账本，不经过服务器。** 钱包（`resident_c` 桶）是 CitySim 内的第四个桶，
  发薪与消费都是**客户端模拟**。多人模式下服务器只对玩家钱包有权威（见 5d），
  因此 NPC 吃掉的午饭不产生任何服务器交易。玩家侧的"250000 假余额"已在同一轮删掉
  （HUD 现在只显示服务器说过的数，见 5d），但单人模式下玩家**没有**属于自己的钱包，
  这条 NPC 经济与玩家钱包之间的桥仍未搭。
- **拥堵是占用量模型，不是车流仿真。** 场里存的是"这一格此刻有多少加权主体"（人 1、车 8），
  稳态由发布速率 ÷ 衰减决定；它能让车速与步速下降，但没有信号灯、没有通行权、没有换道、
  没有事故，车辆仍按格网边随机前进。所以"早高峰"是日程与占用共同产生的**结果**，
  不是路口行为的**仿真**。
- **迁移响应的不是失业率。** CitySim 的 `employed` 只统计店员（11 区合计约 7 万，对 270 万劳动力），
  把它当失业率会让每个居住区都"98% 失业"而持续失血 —— 这是第一版的真实故障。现在迁移响应的
  是就业**变化量**与压力项，因此"绝对失业率"在这个模型里没有意义，只有"本地经济在招还是在关"有意义。
- **新闻是确定性规则，不接远端模型。** 每条标题都由两次测量之差产生并携带 `facts`；
  规范 P267 的"AI 生成"按状态→语言映射实现。没有推送、没有存档，重启后新闻历史为空。
- **快照必须成对取。** `CitySim.snapshot()` 不含人口队列；经济与人口要一起 snapshot / restore，
  否则还原后的区人口与金字塔互不相等（`SimTests` 现在按成对方式断言，`--sim-test` 会立刻报出来）。
  接入后端存档时这条必须一起搬过去。
- **两个客户端会模拟出不同的人口。** CityLife 只在客户端跑，游戏服务器不实例化它。
  同一座城在两台机器上会漂出不同的年龄结构与租金。目前世界一致性只覆盖玩家钱包与建筑。
- **每小时成本翻倍了。** 接生命层前 `per_hour 0.313 ms`，现在 `0.778 ms`（门槛 1.0 ms）。
  余量从 3 倍缩到 1.3 倍；再加需求侧模型（地铁、通勤分担）就会顶到门槛，届时应把新闻评估降频到
  每日一次，而不是抬门槛。
